### UI/UXデザイナー: §6.2 プロパティ表の再設計

**問題:** 現在の§6.2は Node と Pipe のプロパティを混在表示。`valveId` が Node にあると誤解される。

**提案:** Node プロパティ表・Pipe プロパティ表・型別動作マトリクスの3テーブルに分離。

**型別プロパティマトリクス（追加提案）:**

| プロパティ | input | tank | outlet | connection (type省略) |
|-----------|-------|------|--------|---------------------|
| `id` | 必須 | 必須 | 必須 | 必須 |
| `x`, `y` | 必須 | 必須 | 必須 | 必須 |
| `label` | 推奨 | 推奨 | 推奨 | 不要 |
| `type` | `'input'` | `'tank'` | `'outlet'` | 省略 |
| `tankId` | — | 必須 | — | — |

### 化学プラントエンジニア: tankId の明示化

**現行の問題:**
- `V{n}` → `valveId` プロパティで**明示的**に対応（V3 = valveId:3 のパイプ）
- `T{n}` → nodes 配列の出現順で**暗黙的**に対応（T1 = 最初の tank ノード）

**リスク:** ノード配列の並び替えで CSV の `T1=EMPTY` が意図しないタンクを指す。DCS の安全系で位置依存のマッピングは許容できない。

**決定: `tankId` プロパティを追加（Option A）**

```typescript
// types.ts
export interface PIDNode {
  id: string;
  x: number;
  y: number;
  label?: string;
  type?: 'input' | 'outlet' | 'tank';
  tankId?: number;  // CSV条件式 T{n} の参照先。tank のみ。
}
```

```typescript
// sampleData.ts
{ id: 'tank-T1', x: 370, y: 200, label: 'T-1', type: 'tank', tankId: 1 },
{ id: 'tank-T2', x: 370, y: 280, label: 'T-2', type: 'tank', tankId: 2 },
```

tankIdMap 導出を tankId ベースに変更（配列順フォールバックは維持）:
```typescript
export const tankIdMap: Record<string, string> = Object.fromEntries(
  nodes
    .filter(n => n.type === 'tank' && n.tankId != null)
    .map(n => [`T${n.tankId}`, n.id])
);
```

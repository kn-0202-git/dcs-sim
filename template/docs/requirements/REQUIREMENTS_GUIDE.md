# 要件定義書 書き方ガイド

このガイドでは、`REQUIREMENTS.md` の各セクションをどのように記入するか説明します。

## 目的

要件定義書の目的は：
- プロジェクトの目的・背景を明確にする
- スコープ（作るもの/作らないもの）を定義する
- 成功指標を設定する
- 関係者全員が同じ理解を持つ

## 対象読者

- 開発チーム
- プロダクトマネージャー
- ステークホルダー
- LLM（開発支援AI）

## 各セクションの書き方

### 1. 背景と目的

**書くべき内容:**
- なぜこのプロジェクトが必要か（問題点）
- 何を解決したいか（目的）
- 誰のためのものか（受益者）

**良い例:**
```markdown
## 1. 背景と目的
- 背景: 現在の手動タスク管理では、チーム間の進捗共有に時間がかかり、タスクの重複や漏れが発生している
- 目的: チーム全体の生産性を向上させ、タスクの可視化・共有を効率化する
```

**悪い例:**
```markdown
## 1. 背景と目的
- 背景: タスク管理ツールを作る
- 目的: 便利にする
```
（問題: 「なぜ必要か」「何を解決するか」が不明確）

### 2. ステークホルダー / 専門家役

**書くべき内容:**
- プロジェクトに関わる役割とその責務
- 基本的な役割（PM、テックリード、UX/業務設計）は残す
- プロジェクト固有の専門家役を追加

**良い例:**
```markdown
## 2. ステークホルダー / 専門家役
- オーナー/ユーザー: 中小企業のプロジェクトマネージャー
- プロダクトマネージャー役: 要件整理と優先度付け
- テックリード役: 技術選定と実現性評価
- UX/業務設計役: 使い勝手と運用フロー設計
- セキュリティ専門家役: データ保護と認証方式の検討
```

### 3. 何を作るか（プロダクト定義）

**書くべき内容:**
- プロダクトの簡潔な説明（1-2文）
- 使用技術（決定している場合）

**良い例:**
```markdown
## 3. 何を作るか（プロダクト定義）
- タスク管理・共有機能を持つWebアプリケーション
- リアルタイム更新とモバイル対応が特徴
- 使用技術: React + Node.js + PostgreSQL
```

### 4. ゴール / 成功指標（暫定）

**書くべき内容:**
- 測定可能な目標
- 数値化できる指標を含める

**良い例:**
```markdown
## 4. ゴール / 成功指標（暫定）
- タスク管理にかかる時間を50%削減
- チーム間の情報共有遅延を1日以内に短縮
- ユーザー満足度スコア4.0以上（5点満点）
```

**悪い例:**
```markdown
## 4. ゴール / 成功指標（暫定）
- 使いやすくする
- 効率化する
```
（問題: 測定不可能）

### 5. スコープ

**書くべき内容:**

#### 5.1 MVP（Minimum Viable Product）
- 最初のリリースに含める最小限の機能
- 1-3ヶ月で実現可能な範囲

**良い例:**
```markdown
### 5.1 MVP（1か月目の目安）
- ユーザー登録・ログイン
- タスクの作成・編集・削除
- カンバンボード形式での表示
- 基本的なフィルタリング（期限、担当者）
```

#### 5.2 フェーズ2以降
- MVPの後に追加する機能
- 優先度順に記載

**良い例:**
```markdown
### 5.2 フェーズ2以降
- ガントチャート表示
- ファイル添付機能
- 外部カレンダー連携（Google Calendar等）
- モバイルアプリ
```

### 6. 機能要件

**書くべき内容:**
- 機能をカテゴリごとに分類
- 各機能の詳細（入力、処理、出力）

**良い例:**
```markdown
## 6. 機能要件
### 6.1 認証機能
- メールアドレス + パスワードでログイン
- パスワードリセット機能
- セッション管理（2週間有効）

### 6.2 タスク管理機能
- タスクの作成: タイトル、説明、期限、担当者を設定
- タスクの編集: 上記項目の変更が可能
- タスクの削除: 削除前に確認ダイアログを表示
- タスクのステータス変更: ToDo / In Progress / Done
```

### 7. 非機能要件

**書くべき内容:**
- パフォーマンス
- セキュリティ
- 可用性
- 保守性
- スケーラビリティ

**良い例:**
```markdown
## 7. 非機能要件
- パフォーマンス: ページ読み込み時間2秒以内
- セキュリティ: HTTPS必須、パスワードはbcryptでハッシュ化
- 可用性: 稼働率99%以上
- 保守性: コードカバレッジ80%以上
- スケーラビリティ: 同時接続ユーザー1000人まで対応
```

### 8. 関連ドキュメント

**書くべき内容:**
- 他のドキュメントへのリンク（そのまま記載）

### 9. 専門家議論メモ（要約）

**書くべき内容:**
- 重要な決定事項
- 各専門家の視点からのコメント

**良い例:**
```markdown
## 9. 専門家議論メモ（要約）
- PM: MVPは「認証 + タスクCRUD + カンバンボード」に絞り、3ヶ月でリリース
- テックリード: React + Node.jsで進める。DBはPostgreSQLを選定（拡張性重視）
- UX/業務設計: モバイル対応はフェーズ2に延期し、まずデスクトップ版を優先
- セキュリティ専門家: OAuth2.0は将来対応。まずは基本認証で実装
```

### 10. 既存資産

**書くべき内容:**
- 再利用可能な既存コード、ライブラリ、データ

**例:**
```markdown
## 10. 既存資産
- 社内共通のReactコンポーネントライブラリ（UI Kit v2.0）
- ユーザー認証モジュール（Node.js用、JWT対応）
```

### 11. 未決事項 / 追加ヒアリング

**書くべき内容:**
- まだ決まっていない要件
- 今後確認が必要な項目

**例:**
```markdown
## 11. 未決事項 / 追加ヒアリング
- 通知機能の詳細（メール？プッシュ通知？）
- データのエクスポート形式（CSV？Excel？）
- 料金プラン（無料？サブスクリプション？）
```

## チェックリスト

要件定義書を書き終えたら、以下を確認してください：

- [ ] 背景と目的が明確に記載されている
- [ ] ステークホルダーの役割が定義されている
- [ ] プロダクト定義が簡潔で理解しやすい
- [ ] 成功指標が測定可能である
- [ ] MVPスコープが1-3ヶ月で実現可能である
- [ ] 機能要件が具体的に記載されている
- [ ] 非機能要件が記載されている
- [ ] 専門家議論の結果が反映されている
- [ ] 未決事項が明確に記載されている

## よくある間違いと対処法

### 間違い1: スコープが広すぎる

**問題:** MVPに全機能を詰め込む

**対処法:** 「なくても最初のリリースができるもの」はフェーズ2に移動

### 間違い2: 成功指標が曖昧

**問題:** 「使いやすくする」「効率化する」など測定不可能

**対処法:** 数値化できる指標に置き換える（例: タスク作成時間を30秒以内）

### 間違い3: 技術の詳細が多すぎる

**問題:** 要件定義書に実装詳細を書く

**対処法:** 技術詳細は `ARCHITECTURE.md` に移動

### 間違い4: ステークホルダーの視点が不足

**問題:** 開発者視点のみで書かれている

**対処法:** PM、UX、ビジネス視点を含める

## まとめ

良い要件定義書は：
- **明確**: 誰が読んでも同じ理解ができる
- **測定可能**: 成功/失敗が判断できる
- **実現可能**: リソースと時間を考慮している
- **簡潔**: 不要な情報がない

次のステップ:
1. 要件定義書を完成させる
2. `docs/process/PLAN.md` で開発計画を立てる
3. `docs/architecture/ARCHITECTURE.md` で技術設計を記載
